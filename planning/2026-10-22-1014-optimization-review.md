# 慢行 · SenseWalk 仓库整体审查与优化建议

- **时间戳**：2026-10-22 10:14（CST）
- **审查基线**：main @ `379d093`（2026-10-21，阶段收口合并）
- **审查范围**：仓库结构、提交与协作流程、CI、发布与许可、文档体系、代码与测试

## 一、总体判断

仓库运转健康的部分先说清楚：双工作流（Android build + Collaboration handoff checks）近期运行全绿；JVM 测试从 T03 的 143 个增长到 312 个；多代理协作（ZCode / Antigravity / Trae-design / Codex）有 registry、看板、交接与独立评审，森林阶段已于 2026-10-21 收口；状态文档保持诚实，未验证项不冒充完成。

问题集中在三处：**许可署名靠人工补丁、仓库体积失控、规划文档散落多处且时效不一**。以下按优先级列出。

## 二、优化建议

### P0-1 署名必须进发布模板，不要再靠人工逐个补丁

- **证据**：`.github/workflows/android.yml` 的 release notes 模板至今没有署名块。2026-10-21 新发布的 build-224 再次漏署名，APK 已被下载 5 次。此前 build-87 / 109 / 153 / 176 四个 Release 都是发布后人工补丁。
- **风险**：脚步音（gravitysound.studio）与鸟鸣（DivyaCM）为 CC BY 4.0，对外分发必须署名；每发一个新 build 就重新暴露一次。
- **建议**：
  1. 把 `## Audio credits` 署名块直接写进 workflow 的 release-notes 模板（heredoc），一次固化、长期有效；
  2. 给 build-224 立即补上署名（与前四次同一文案）；
  3. About 页应用内署名（ASSETS.md 记为「后续打磨」）一并排期，与模板固化形成双保险。

### P0-2 仓库体积治理：310 MB 且还在快速膨胀

- **证据**：仓库体积约 310 MB（2026-10-13 时约 35 MB，9 天涨了约 9 倍）。全仓 2,360 个文件里 `design/` 占 1,576 个、`docs/` 647 个，`app/` 只有 116 个。最大的文件是雨林 preflight 的负向测试 fixture：多份 8.3 MB 的 PNG 与 5.5 MB 的 WebP 直接入了 git。
- **影响**：clone / CI checkout / 源码交接 ZIP 都在变慢变大；git 历史只增不减，越往后越难瘦身。
- **建议**：
  1. 负向 oversize fixture 改为脚本按需生成（它们本来就是程序化构造的超限样本），不再入库；已入库的从工作树移除并加入 `.gitignore`；
  2. 确需长期保存的大二进制走 Git LFS 或发布工件，不要进主干历史；
  3. 加一道 CI 体积守卫：单文件 > 1 MB 且不在 `app/src/main/assets` 白名单内时报警；
  4. 选一个低峰窗口评估历史清理（如 BFG），清理前全员同步。

### P1-3 规划与建议统一入口（本次已落地 `planning/`）

- **现状**：规划类文档散落在 `DEVELOPMENT.md`、`docs/collaboration/`（ROADMAP、plans/ 按日期目录、decisions/）、`design/`、`docs/plan.html`、`ASSETS.md` 多处，新人或新代理要拼图才能找到全貌。
- **本次动作**：新建仓库根目录 `planning/` 作为统一入口，`planning/README.md` 索引全仓规划与建议文档；今后的整体审查与优化建议按 `YYYY-MM-DD-HHMM-主题.md`（CST）命名放入本目录，用时间戳区分版本。
- **说明**：`DEVELOPMENT.md` 等存量文档被 README、设计包、交接文档大量以相对路径引用，本次未物理搬迁，避免断链。如需物理搬迁，应单独立项并全量改链后再执行。

### P1-4 DEVELOPMENT.md 时效性与「当前进度」脱节

- **证据**：文件头仍标 v0.8 / 2026-10-12，§0 停留在 2026-10-14 追加核查（T06 后），而 main 已推进到 2026-10-21 的森林渲染阶段收口与三代理交接。文件自称「规则与交付状态以本文件为准」，但交付状态实际以 `docs/collaboration` 的 registry 为准，两处真相开始漂移。
- **建议**：二选一并写明纪律——要么每次阶段收口同步刷新 §0 并 bump 文件头版本与日期；要么 §0 瘦身为指针（规则留本文件，进度只指向 registry / ROADMAP），消除双真相。

### P1-5 过期 PR 及时关闭

- **证据**：PR #25（SW-006 R1 雨林草案）已被 PR #35（R2）取代，但仍处于 open 状态，停留在 2026-10-19。
- **建议**：关闭 #25 并注明 superseded by #35；形成惯例：同一任务的新修订 PR 打开时，旧稿 PR 同步关闭并互链。

### P1-6 真机验证债务不要再漂移

- **证据**：M1 退出条件中的真人标准 800 m 手动验收、真机耳机 / 来电、锁屏 15 分钟、真实计步，自 2026-10-13 起一直挂在「待验证」，是目前唯一卡住 M1 宣布完成的事项；其余机制与素材均已有证据。
- **建议**：排一个真机验证专日，按 DEVELOPMENT.md §20.3 清单逐项执行并回填证据（设备型号、系统版本、结果），一次收口，而不是继续随缘推进。

### P2-7 工具脚本可发现性

- **证据**：仓库语言构成里 Python（629 KB）已超过 Kotlin（566 KB），多为 QA / 预检 / 协作脚本，但入口与用途说明分散。
- **建议**：在 `tools/` 或脚本所在目录补一份索引（脚本名、用途、入口命令、输入输出），避免工具变成只有作者知道的 tribal knowledge。

### P2-8 design 历史阶段归档

- **证据**：`design/` 1,576 个文件多为已完成阶段的候选、预览与验证证据，日常浏览与检索噪音大。
- **建议**：按阶段打包归档（每阶段一个压缩包或移至归档分支 / 发布工件），主干只保留当前阶段文件与索引，老阶段按需解包。
