## 发现与退回原因

### 1. P-01 (P1)：detector 硬件存在但注册失败时，脚步音回退被关闭（静音行走）
- **触发路径**：
  在 `StepSensorSource.kt` 中：
  ```kotlin
  if (port.hasDetector) {
      port.registerDetector(onDetectorStep) // 返回值被直接丢弃！
  }
  val hasDetector: Boolean get() = port.hasDetector // 仅代表硬件存在
  ```
  在 `WalkForegroundService.kt:192` 中：
  ```kotlin
  sensory.stepAudioFromDistance = !(sensorSource.isStarted && sensorSource.hasDetector)
  ```
- **实际缺陷**：当设备具有 detector 传感器但因权限缺失、驱动占用等原因导致 `port.registerDetector` 返回 `false` 时，`sensorSource.hasDetector` 依然为 `true`，导致 `stepAudioFromDistance` 被设为 `false`。由于监听实际未挂载，detector 步伐事件永远不会到达；而基于距离的脚步音又被关闭，导致实走出现**有距离增量却全程无脚步声、无振动**的严重体验退化。
- **应有行为**：`StepSensorSource` 必须准确记录 detector 的实际注册成功状态（例如 `isDetectorRegistered`），服务层据此决定是否启用距离脚步音回退，并增加包含真实注册失败端口与服务装配的调用链测试。

### 2. P-02 (P1)：“同刻合并步数带回”与实际计数基线不一致（步数丢失）
- **触发路径**：
  在 `RealWalkEngine.kt:111-114` 中：
  ```kotlin
  if (intervalMs <= 0L) {
      // 同刻合并：本事件 0 米；只推进计数基线，时间基线不动——
      // 被合并的步数在下一个正间隔事件中统一计距并封顶
      lastAcceptedCount = stepCount
      return StepDelta(0f, 0L)
  }
  ```
- **实际缺陷**：代码直接将 `lastAcceptedCount` 推进至当前 `stepCount`，并未缓存未消耗的 pending 增量。在下一个正间隔事件（如第 4 个事件）到达时，增量计算公式为 `steps = stepCount - lastAcceptedCount`，其起点已被更新为同刻最后一次的读数。通过 `test_p02_same_millisecond_batching_step_loss_counterexample` 证实：在低步数、未被 1.4 m/s 速度帽饱和的场景下，同刻到达的步数被彻底丢弃，而非合并带回。
- **应有行为**：同刻事件若声明为合并带回，必须显式保留 pending 增量或维持前次接受基线，并在后续正间隔计算中计入合规带回（且受当前有效间隔速度封顶保护）；或在协议中明确同刻丢弃语义，保持代码与交接说明一致。
